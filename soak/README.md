# Sigul soak and chaos harness

Sustained load against the real stack while clients misbehave the way
real ones do, with the daemons' memory, descriptors and sockets
watched throughout. Its job is to answer the question the functional
suites cannot: what happens to everyone else when one client, one
link or one process goes wrong, and does the service come back on its
own.

## Why this exists

Sigul is strictly serial. The bridge pairs one server connection
with one client at a time; there is no concurrency anywhere
in the pipeline. That makes it unusually exposed to a single bad peer:
a client that connects and says nothing, or authenticates and then
freezes, is not a degraded request - the whole service is blocked
for as long as that client stays. The production deadlock that
motivated patches 06 and 07 was one instance of this shape. This
harness exists to find the others before they find us.

## What it does

The `pr` profile, about 30 minutes, looks like this:

```text
ramp      1 → 2 → 4 → 8 clients, 45s each     finds the backlog cliff
baseline  2 min clean load at 3 clients       reference latency, leak start
faults    11 faults, 20 min in total          the actual test
cooldown  5 min clean load                    compared against baseline
```

Each fault is held for 30-90 s and followed by 30-90 s of clean
running in which recovery is measured; the exact plan is the
`FaultSlot` list in `harness/profiles.py`.

Steady load is generated by [Locust](https://locust.io) driving the
real `sigul` CLI from the client image under test: `list-users`,
`list-keys`, `sign-text`, `sign-data` at 1 MiB and 64 MiB, weighted
towards the cheap control-plane calls CI makes most. Every invocation
is a genuine double-TLS request.

Faults are injected from the same container. Three families:

<!-- markdownlint-disable MD013 -->

| Family    | Mechanism                                                                       | Examples                                                  |
| --------- | ------------------------------------------------------------------------------- | --------------------------------------------------------- |
| `client_` | raw sockets, or the real CLI abused with signals                                | connect and hang, SIGSTOP mid-request, RST, backlog flood |
| `net_`    | [Toxiproxy](https://github.com/Shopify/toxiproxy) toxics in front of the bridge | latency, bandwidth cap, reset, blackhole (no FIN, no RST) |
| `proc_`   | Docker API                                                                      | restart or freeze the bridge or server                    |

<!-- markdownlint-enable MD013 -->

Toxiproxy sits transparently on both bridge ports via an `/etc/hosts`
override in the server and runner containers, so the stack's own
configuration is untouched and the server→bridge link - the one the
production incident died on - can be blackholed from inside the path.

Every five seconds a sampler records RSS, CPU, process count, open
descriptors, zombies and TCP socket states for the bridge and server.

## What it judges

**Per fault**: the longest gap between successful requests from the
fault's start until service resumed (the *stall*), and the time from
the fault's end to the first success (*recovery*). A misbehaving client
should not stall the service for more than 30s, because the bridge
ought to shed it; a fault that removes the service outright (frozen
bridge, blackholed link) is judged on recovery alone.

**Invariants**, absolute: recovery after every fault; RSS trend under
30 MB/h from a fit over the whole run; descriptors and CLOSE-WAIT
sockets back to where they were in the baseline phase; no zombies;
and each daemon sampled for at least half the run, so a silent
sampler cannot pass as a clean one.

**Regressions**, relative to a committed `baseline-<profile>.json`:
p95 latency per task within +50 % or +250 ms of the baseline,
whichever is larger; success rate within 5 points.

### Expected failures

`harness/expectations.json` lists faults and invariants known to fail
on current code, per profile, each with the issue tracking the defect.
Those report as **xfail** and do not fail the run. For a fault the
marker covers the stall during its window only: failing to recover
once the fault has ended, or a harness error injecting it, always
fails the run. If one starts *passing* it
reports as **xpass** and the run fails - the marker is stale, and
whoever fixed it should remove the entry and close the issue. This is
how the suite stays green and useful while the defects it has found
are being worked through, without anyone forgetting them.

## Running it

```bash
# Images tagged as the deploy script expects, or set SIGUL_*_IMAGE
docker tag ghcr.io/lfreleng-actions/sigul-docker-k8s/server:v2.2.4 server-linux-arm64-image:test
# ... bridge, client likewise

./soak/run-soak.sh smoke      # ~3 min: proves the harness works
./soak/run-soak.sh pr         # ~30 min: the pull-request gate
./soak/run-soak.sh nightly    # hours: everything, repeated
```

`./soak/run-soak.sh --keep` runs the default `smoke` profile; the
profile and `--keep` may be given in either order.

`run-soak.sh` deploys the stack with `scripts/deploy-sigul-infrastructure.sh`,
provisions the client with `scripts/setup-client.sh`, brings up
Toxiproxy, re-points the server through it, builds the runner image on
top of the client image, and runs the profile. Add `--keep` to leave
the stack up afterwards. Results land in `soak/results/`; a previous
run's results are moved to `soak/results-<timestamp>/` rather than
overwritten, so an A/B comparison has both to hand:

<!-- markdownlint-disable MD013 -->

| File                     | Contents                                                    |
| ------------------------ | ----------------------------------------------------------- |
| `report.md`              | The verdict, in the form CI puts in the job summary         |
| `results.json`           | Everything the report is built from; diffable across runs   |
| `latency.png`            | Every request over time, fault windows shaded               |
| `resources.png`          | RSS, descriptors and socket states over time                |
| `requests.csv`           | One row per `sigul` invocation                              |
| `samples.csv`            | One row per unit per sampler tick                           |
| `timeline.csv`           | Phase and fault boundaries                                  |
| `locust*`                | Locust's own statistics and HTML report                     |

<!-- markdownlint-enable MD013 -->

To re-run the analysis on existing results:

```bash
docker compose -f docker-compose.sigul.yml -f soak/compose.soak.yml \
    run --rm --no-deps soak-runner pr --analyse-only
```

### Comparing images

Everything is parameterised by image, so an A/B is two runs:

```bash
export SIGUL_SERVER_IMAGE=ghcr.io/.../server:v2.2.4   # bridge, client likewise
./soak/run-soak.sh pr
export SIGUL_SERVER_IMAGE=server-linux-arm64-image:test
./soak/run-soak.sh pr                                 # previous run kept
diff <(jq .faults soak/results-*/results.json) \
     <(jq .faults soak/results/results.json)
```

## Layout

```text
soak/
├── run-soak.sh              host-side orchestrator
├── compose.soak.yml         overlay: toxiproxy + runner + /etc/hosts redirect
├── Dockerfile               runner image = client image + locust + docker SDK
└── harness/
    ├── __main__.py          run one profile end to end
    ├── profiles.py          smoke / pr / nightly: durations, faults, weights
    ├── locustfile.py        SigulUser tasks and the load shape
    ├── scheduler.py         walks the fault plan, writes timeline.csv
    ├── sampler.py           resource readings, writes samples.csv
    ├── analyze.py           verdict, report.md, results.json, charts
    ├── target.py            how to measure and disturb the stack (Docker; K8s later)
    ├── expectations.json    known defects, as xfail markers
    └── faults/
        ├── base.py          Fault interface, Toxiproxy client
        ├── clients.py       client_* faults
        ├── network.py       net_* faults
        └── process.py       proc_* faults
```

## Adding a fault

Subclass `Fault` in the appropriate module, give it a `name`,
`description` and `implication` (what a human should conclude if the
service does not cope), set `service_possible_during = False` if the
fault removes the service outright, write `start()` and an
idempotent `stop()`, and add the class to that module's registry
tuple. Then add a `FaultSlot` to a profile. Nothing else needs to
know about it.

## Kubernetes

The harness reaches the stack through `target.Target` and nothing
else. A `KubernetesTarget` providing the same six operations against a
kind cluster running the production chart would let the identical fault
plan exercise probe-driven recovery, which Compose cannot. That is the
intended next step once the Compose runs have settled.
